Section 00

What We Built & Why

This project is a RAG (Retrieval-Augmented Generation) system — a type of AI application that answers questions by first searching a knowledge base (your documents), then passing the most relevant text to a Large Language Model (LLM) to generate an answer. Unlike asking ChatGPT, a RAG system only answers from your documents, which means answers are accurate, cited, and private.

We built this for 38 company HR policy documents. An employee can now ask "How many days of maternity leave do I get?" and receive an accurate answer with a source citation — without reading through 400 pages of policy manuals.

Why RAG instead of just uploading PDFs to ChatGPT?
Three reasons: (1) Privacy — company policies contain sensitive data that should not leave your infrastructure. (2) Accuracy — LLMs hallucinate; RAG grounds answers in real documents. (3) Cost — after the one-time embedding cost, queries are nearly free locally.

The Swap Point Pattern — Most Important Concept

The entire LLM switching mechanism lives in one place:

def get_llm():
    mode = os.getenv("LLM_MODE", "ollama").lower()
    if mode == "ollama":
        return Ollama(model="phi3:mini", request_timeout=300.0, context_window=4096)
    if mode == "claude":
        return Anthropic(model="claude-sonnet-4-20250514", api_key=...)
    # Switch LLM_MODE in .env — zero code changes required
Why this matters for your career: This is the Dependency Inversion Principle — your business logic depends on an abstraction (get_llm), not a concrete vendor. In production systems, teams use this exact pattern to avoid vendor lock-in. Switching from OpenAI to Claude to a self-hosted model becomes a config change, not a code refactor.

🔴Python 3.14 Compatibility — 4 cascading conflicts

Python 3.14 was too new for the ecosystem. Packages like numpy 1.26.x and pillow 10.x had no pre-built wheels for Python 3.14 and needed a C compiler to build from source — which wasn't installed.

Never use a Python version released less than 6 months ago on a real project. The package ecosystem takes time to catch up. Python 3.12 would have had zero of these conflicts. Always check pypi.org for wheel availability before choosing a Python version.

🔴requirements.lock accidentally gitignored

I added requirements.lock to .gitignore by mistake. Lock files should be committed — they're your reproducibility guarantee.

Fix

Removed the entry from .gitignore and re-staged the file. Lesson: think carefully before adding anything to .gitignore.

Phase 03 · ~1.5 hrs actual
Data Pipeline

PDF Ingestion Pipeline

The most critical phase. Bad ingestion = bad retrieval = wrong answers regardless of LLM quality. We built app/ingest.py and wrote the golden Q&A test set before writing a single line of pipeline code.

The Golden Q&A Test Set — Do This First, Always

Before building the pipeline, we wrote tests/golden_qa.txt — 15 real questions with known correct answers from the actual PDFs. This became our ground truth for evaluating retrieval quality.

Why write tests before code? In RAG, it's easy to build a pipeline that "works" but returns wrong answers. Without a test set you have no way to know. The golden Q&A transforms "seems to work" into a measurable score: 15/15 retrieval, 12/15 end-to-end.

What We Built in ingest.py

# 1. Load PDFs (text extraction via PDFReader/pypdf)
docs = SimpleDirectoryReader("pdfs/", required_exts=[".pdf"],
    file_extractor={".pdf": PDFReader()}).load_data()

# 2. Configure chunking — 768 tokens, 100 token overlap
splitter = SentenceSplitter(chunk_size=768, chunk_overlap=100)

# 3. Connect to persistent ChromaDB
client = chromadb.PersistentClient(path="vector_store/")
collection = client.get_or_create_collection("policy_docs")

# 4. One call: chunk → embed → store
index = VectorStoreIndex.from_documents(docs,
    storage_context=StorageContext.from_defaults(
        vector_store=ChromaVectorStore(chroma_collection=collection)),
    embed_model=get_embedding_model(),
    transformations=[splitter])

Chunking Strategy Explained

chunk_size=768: Each chunk is up to 768 tokens (~3000 characters). For dense policy text, this preserves complete clauses and sub-sections without splitting them awkwardly.

chunk_overlap=100: Adjacent chunks share 100 tokens of context. This prevents losing information that spans a chunk boundary — for example, a sentence that starts on one chunk and ends on the next.

When to tune chunk_size: If answers are cut off mid-sentence → increase to 1024. If retrieved chunks are too broad and not focused on the answer → decrease to 512. Always delete vector_store/ and re-run ingest after changing chunk settings — stale vectors will corrupt your results.

Retrieval Result: 15/15

After ingestion, we tested retrieval directly (bypassing the LLM) by checking whether the correct source document appeared in the top-3 results for each golden question. Result: 15 out of 15 passed on the first run.

Roadblocks

🔴SimpleDirectoryReader returning raw PDF binary, not text

In LlamaIndex 0.14.x, SimpleDirectoryReader without an explicit file extractor reads PDFs as raw bytes. The character counts looked large (175K chars per document) but the content was binary PDF encoding — completely useless for search.

# Wrong — returns raw binary
docs = SimpleDirectoryReader("pdfs/").load_data()

# Correct — uses pypdf for proper text extraction
from llama_index.readers.file import PDFReader
docs = SimpleDirectoryReader("pdfs/", required_exts=[".pdf"],
    file_extractor={".pdf": PDFReader()}).load_data()
Fix

Installed pypdf and llama-index-readers-file, then passed file_extractor={".pdf": PDFReader()} explicitly. Always verify extracted text looks like readable content, not binary gibberish.

🟡"1 page per PDF" — misleading output

All 38 PDFs initially showed as "1 page" each. This was because LlamaIndex 0.14.x (before adding PDFReader) was loading each PDF as a single document object, not per-page. After switching to PDFReader, the correct 378 pages loaded correctly.

Lesson

Always spot-check extracted text content, not just document count. print(docs[0].text[:500]) immediately reveals whether you have real text or binary garbage.

Phase 04 · ~3 hrs actual
Query Engine

Query Engine & Answers

Building app/query.py — loads the existing index, retrieves relevant chunks, and passes them to the LLM with a strict prompt that prevents hallucination and enforces source citation.

The Custom Prompt Template

The prompt template is where you control the LLM's behaviour. Ours enforces three rules:

POLICY_QA_TEMPLATE = PromptTemplate(
    "You are a helpful HR policy assistant.\n"
    "Answer using ONLY the policy context provided below.\n"
    "Rules:\n"
    "  1. Base your answer strictly on the context — no outside knowledge.\n"
    "  2. Always cite the policy name and page number.\n"
    '  3. If not found in context: "This information is not in the provided policy documents."\n'
    "  4. Be concise and direct.\n\n"
    "Context:\n---------------------\n{context_str}\n---------------------\n\n"
    "Question: {query_str}\n\nAnswer:"
)
Rule 3 is the anti-hallucination guard. Without it, LLMs will confidently make up policy details that don't exist. The explicit fallback phrase ("This information is not in the provided policy documents") is better than a fabricated answer — users learn to trust the system because it's honest about its limits.

Critical Rule: Never Re-embed on Query

# WRONG — re-embeds everything on every query (very slow, expensive)
index = VectorStoreIndex.from_documents(docs, ...)

# CORRECT — loads existing index from ChromaDB (fast, free)
index = VectorStoreIndex.from_vector_store(vector_store,
    embed_model=get_embedding_model())

Observability — Built In From Day One

Every query logs the retrieved source nodes, their relevance scores, and text previews. This is how you debug wrong answers:

for node in response.source_nodes:
    print(f"score={node.score:.4f} | {node.metadata['file_name']} p.{node.metadata['page_label']}")
    print(f"  {node.text[:150]}...")
Debugging guide (from the tracker): If answers are wrong — 80% of the time the retrieved chunks are wrong (go back to Phase 3 chunking). 20% of the time the chunks are right but the prompt is bad (fix the template). Always check source nodes first before blaming the LLM.

Roadblocks

🔴llama3.2 requires 15.9 GiB RAM — machine only has 10.6 GiB available

The default llama3.2 model (3B parameters, full precision) needs 15.9 GiB RAM for KV cache allocation. The machine only had 10.6 GiB available.

Fix

Switched to smaller local models. Eventually settled on phi3:mini with an explicit context_window=4096 override (see next roadblock).

🔴Claude API — zero credits on both keys

Both Anthropic API keys provided had valid authentication but zero credit balance. The API returns HTTP 400 with "credit balance too low" — not 401 (unauthorized), which makes it easy to confuse with a code error.

Fix

Switched to local models. Claude can be re-enabled by adding credits at console.anthropic.com and changing LLM_MODE=claude in .env. No code changes needed.

🔴phi3 (default tag) = 14B model = 50 GiB RAM required

Running ollama pull phi3 downloads the 14B parameter version. Ollama pre-allocates KV cache for the model's full context window (128k tokens), which translates to ~50 GiB RAM.

Fix (two steps)

Step 1: Use phi3:mini (3.8B parameters, 2.2 GB on disk).
Step 2: Even phi3:mini has a 128k context window. Ollama pre-allocates memory for the full window. Override with context_window=4096 in the Ollama LlamaIndex wrapper — this tells Ollama to only allocate KV cache for 4096 tokens, reducing RAM from ~50 GiB to ~2 GiB.

return Ollama(model="phi3:mini", request_timeout=300.0, context_window=4096)
🟡ReadTimeout — single slow query crashing the full evaluation run

phi3:mini on CPU takes 60-180 seconds per query. Some policy chunks are larger and occasionally exceeded the timeout, crashing the entire 15-question evaluation.

Fix — production-grade timeout handling

Wrapped each query in try/except that catches timeout exceptions, logs them, and continues to the next question:

try:
    result = ask(q, engine=engine, verbose=False)
except Exception as e:
    if "timeout" in str(e).lower():
        print(f"  [TIMEOUT] Query took too long — skipping")
    else:
        print(f"  [ERROR] {str(e)[:120]}")
Phase 05 · ~30 min actual
API Layer

FastAPI Backend

Wrapping the AI logic behind a proper HTTP API. The key principle: FastAPI is thin. It handles HTTP concerns only — routing, validation, error handling. All AI logic stays in query.py and ingest.py.

Three Routes

RouteMethodPurposeResponse
/healthGETServer liveness + config check{"status":"ok","llm_mode":"ollama"}
/queryPOSTAsk a question{"answer":"...","sources":[...]}
/ingestPOSTRe-index all PDFs{"status":"done","chunk_count":378}

Two Important Implementation Details

1. CORS Middleware — without this, the browser blocks Streamlit (port 8501) from calling the API (port 8000):

app.add_middleware(CORSMiddleware,
    allow_origins=["http://localhost:8501"],  # Streamlit's port
    allow_methods=["*"], allow_headers=["*"])

2. Lazy loading the query engine — loading ChromaDB on every request would be wasteful. Load once at first request, cache for subsequent calls:

_query_engine = None
def get_engine():
    global _query_engine
    if _query_engine is None:
        _query_engine = load_query_engine()  # runs once
    return _query_engine
Auto-generated docs: FastAPI generates a full Swagger UI at http://localhost:8000/docs. You can test all routes interactively in the browser without writing any curl commands. This is one of FastAPI's biggest practical advantages.
Phase 06 · ~30 min actual
User Interface

Streamlit Chat UI

A complete chat interface in under 130 lines of Python. No JavaScript, no React, no CSS required.

Key Streamlit Concepts Used

1
st.session_state — persistent chat history
Streamlit re-runs the entire script on every user interaction. st.session_state persists data across reruns. Without it, the chat history disappears on every message.
2
st.chat_message — built-in chat UI
Renders user/assistant message bubbles with proper styling. No CSS needed.
3
st.chat_input — blocks until user submits
Returns the user's text when submitted, None otherwise. Use the walrus operator: if prompt := st.chat_input(...).
4
st.spinner — loading state
Wraps the API call so the UI shows "Searching policy documents..." instead of appearing frozen during the 60-second inference.
5
st.expander — collapsible source citations
Source citations are shown in a collapsed expander under each answer. They don't clutter the conversation but are available for users who want to verify.

What the Full Stack Looks Like Running

# Terminal 1 — API server (keep running)

# Terminal 2 — Streamlit UI
streamlit run ui/streamlit_app.py

# Open in browser
http://localhost:8501
Response time reality: With phi3:mini on CPU, each answer takes ~60 seconds. The spinner hides the wait. With Claude API or a GPU, this drops to 3-5 seconds. The architecture is correct — only the hardware limits performance.

Career Takeaways

Key Concepts for Industry Readiness

Architecture Pattern

The Swap Point / Dependency Inversion

One file (config.py) owns all vendor decisions. Everything else imports from it. This is how production systems avoid vendor lock-in — switching LLMs is a one-line config change.

Secret Management

.env + .env.example Pattern

The committed template shows what secrets are needed. The actual secrets file is gitignored. Every professional project uses this. Never hardcode API keys — ever.

Reproducibility

requirements.txt vs requirements.lock

requirements.txt = intent (human-readable). requirements.lock = exact state (pip freeze). Without a lock file, two machines can produce different installs with different bugs.

RAG Fundamentals

Retrieval vs Generation Are Separate

Retrieval quality (did we find the right chunk?) and generation quality (did the LLM answer correctly?) are independent problems with independent solutions. Debug them separately.

Testing Strategy

Golden Q&A Before Code

Write your test cases before building the pipeline. This converts "seems to work" into a measurable score. Used by every serious ML team in production.

Observability

Log Everything at Inference Time

Always log retrieved chunks, scores, and sources alongside answers. 80% of wrong answers come from retrieval failures — you can't debug what you can't see.

API Design

Keep API Layers Thin

FastAPI handles HTTP. AI logic lives in query.py and ingest.py. This separation means you can test AI logic independently of HTTP concerns, and swap frontends without touching AI code.

Local-First AI

Embeddings Always Stay Local

Even when using Claude for answers, the embedding model runs locally. Embeddings are one-time cost; running them through an API means paying on every ingest. Local embeddings = free forever.

Hardware Awareness

Model Size vs Available RAM

Model file size (on disk) ≠ RAM required at inference. A model with a 128k context window pre-allocates KV cache for the full context — which can be 10-50x the model file size. Always check context window requirements.

Production Thinking

Never Crash on a Single Failure

The timeout try/except pattern is how real systems are built. One slow query should not kill a batch evaluation run or a production server. Isolate failures, log them, continue.
